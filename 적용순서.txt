저장 재시도 패치 적용 순서

1. Supabase SQL Editor에서 20260914_logs_save_retry.sql 전체를 실행합니다.
   중복 그룹 전체를 public.logs_minute_duplicate_backup_20260914에 백업한 뒤 가장 큰 id 한 건을 유지합니다.
   날짜·분 유일 인덱스와 오래된 관측치 덮어쓰기 방지 트리거를 추가합니다.
   전체 작업은 트랜잭션입니다. 오류가 나면 배포하지 말고 오류를 확인하세요.
   잠금 획득 제한은 5초입니다. lock timeout이면 잠시 뒤 SQL 전체를 다시 실행할 수 있습니다.
   새 SQL은 제공된 001 마이그레이션의 logs 및 market_data 구조를 전제로 합니다.
2. app/api/market/live/route.ts를 프로젝트의 같은 위치에 복사합니다.
3. npm run typecheck, npm run build 성공 후 npx vercel --prod로 배포합니다.

변경 내용
- 저장 전 조회→삽입/수정 분기를 날짜·분 기준 원자적 upsert로 교체합니다.
- 최대 총 3회, 동일 JSON 재전송. 408/429/500/502/503/504 및 연결/시간초과만 재시도합니다.
- 각 시도 최대 8초, 재시도 간격 0.5초/1초. 저장 단계 최대 26초이며 수집 시작 후45초를 넘겨 새 저장 시도를 하지 않습니다.
- DB가 저장한 뒤 응답만 유실돼도 같은 날짜·분으로 재전송하므로 중복 행이 생기지 않습니다.
- 같은 분에 더 최신 capturedAt이 저장돼 있으면 오래된/동일한 재시도 업데이트를 무시합니다.
- 정상 응답 saveAction은 upserted, saved/ok는 true입니다. 실패하면 HTTP503입니다.
- 앞서 적용한 실패 상태 코드 및 DB 오류 로그 개선을 포함합니다.
- 수집 시작45초 이후에는 부가 업종 저장을 생략하여 응답 예산을 확보합니다.

변경하지 않는 내용
KIS 키·토큰 발급·cron 일정·시장폭 원본 0·과거 누락 데이터는 변경하지 않습니다.
이 패치만으로 DB 장애를 없애거나 모든 누락을 보장해서 방지할 수는 없습니다.
